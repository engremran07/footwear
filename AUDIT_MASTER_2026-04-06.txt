ISSUE-001 | CRITICAL | FINANCIAL | Agent 03
File: app/lib/providers/invoice_provider.dart (voidInvoice method)
Description:
  voidInvoice() computes the reversal delta as: -total (for sale), +total (for return).
  But if partial payment was already received at invoice creation, balance was only
  incremented by (total - amountReceived). Voiding then reverses by -total, which is
  more than was added, resulting in an overcredit equal to amountReceived.

  Example:
    Invoice created: total=5000, amountReceived=2000
    → balance += 3000 (correct at creation)
    Voided: reversalDelta = -5000
    → balance -= 5000 (WRONG — net effect is -2000 overcredit to customer)

Evidence:
  invoice_provider.dart ~L452:
    final reversalDelta = type == InvoiceModel.typeSale ? -total : total;

Risk: Customer account shows negative balance after void — can create phantom credit
  that is used for future purchases or payroll fraud.

Fix:
  Read the invoice's outstanding_amount from the snapshot before reversing.
  The outstanding_amount = total - amount_received was stored at creation.
  Reverse only the outstanding_amount (the delta that was actually applied to balance).

  final data = invSnap.data()!;
  final amountReceived = (data['amount_received'] as num?)?.toDouble() ?? 0;
  final outstandingDelta = total - amountReceived;
  final reversalDelta = type == InvoiceModel.typeSale
      ? -outstandingDelta
      : outstandingDelta;

  STATUS: ✅ FIXED IN THIS PATCH (see implementation section)
Effort: S

ISSUE-002 | CRITICAL | FINANCIAL | Agent 03
File: app/lib/providers/invoice_provider.dart (markAsPaid method)
Description:
  markAsPaid() only updates invoice.status to 'paid'. It does NOT:
  - Create a 'cash_in' transaction for the payment received
  - Decrement customer.balance by the outstanding amount
  - Update outstanding_amount on the invoice doc

  When admin marks an 'issued' (0% paid) invoice as paid via the UI button,
  the customer's balance remains unchanged. The ledger is permanently out of sync:
  - Invoice says: paid
  - Customer balance says: still owes full amount
  - No cash_in transaction exists
  This is CA-grade integrity failure and a fraud vector (admin can mark as paid
  without cash actually flowing, while balance remains high => double collection risk)

Evidence:
  invoice_provider.dart ~L464:
    await db.collection(Collections.invoices).doc(invoiceId).update({
      'status': InvoiceModel.statusPaid,
      'updated_at': Timestamp.now(),
    });

Risk: Misrepresents outstanding amounts. Breaks profit/loss reporting.
  Enables fraudulent "paid" status without payment.

Fix:
  markAsPaid() must:
  1. Accept amountToSettle: double (outstanding_amount from invoice)
  2. Accept customerId: String and paymentReceivedBy: String
  3. Create a cash_in transaction in batch
  4. Update customer.balance via FieldValue.increment(-amountToSettle)
  5. Update invoice: status=paid, amount_received+=amountToSettle, outstanding_amount=0

  STATUS: ✅ FIXED IN THIS PATCH (see implementation section)
Effort: M

ISSUE-003 | CRITICAL | DATA INTEGRITY | Agent 11
File: app/lib/providers/transaction_provider.dart (allTransactionsProvider)
Description:
  allTransactionsProvider queries: .where('deleted', isNotEqualTo: true).
  Firestore isNotEqualTo semantics: only returns documents where the 'deleted' FIELD
  EXISTS and its value != true. Documents without the 'deleted' field are EXCLUDED.

  None of the transaction create paths (create(), createSellerSale(), createReturn(),
  InvoiceProvider.createSaleInvoice cash_out tx, cash_in tx, ProductNotifier
  transferToSeller inventory_tx, CustomerNotifier markAsBadDebt write_off tx)
  include 'deleted: false' in the batch.set() calls.

  RESULT: allTransactionsProvider admin list returns ZERO RESULTS on new environments.
  Existing pre-migration transactions without the 'deleted' field are also invisible.

Evidence:
  transaction_provider.dart L82:
    batch.set(txRef, {
      'shop_id': shopId, ... // NO 'deleted': false field
    });

Risk: Admin transaction ledger is completely empty. Financial audit trails are inaccessible.
  All revenue reporting is zero until data migration runs.

Fix:
  1. Add 'deleted': false to ALL batch.set() calls for transaction documents.
  2. This applies to: TransactionNotifier.create(), createSellerSale(), createReturn(),
     InvoiceNotifier batch transaction writes, ProductNotifier.transferToSeller()

  STATUS: ✅ FIXED IN THIS PATCH (see implementation section)
Effort: M

ISSUE-004 | CRITICAL | DATA INTEGRITY | Agent 11
File: app/lib/providers/user_provider.dart (updateUser method)
Description:
  updateUser() writes to two Firestore documents via two separate await calls:
    await db.collection(Collections.users).doc(uid).update({...});
    await db.collection(Collections.routes).doc(newRouteId).update({...});
  These are NOT in a WriteBatch. If network drops between the two writes:
  - User doc is updated with new assigned_route_id
  - Route doc still has old assigned_seller_id
  The system is left in an inconsistent state. Seller cannot create transactions
  (isSellerForRoute() rule check fails on stale route doc).

Evidence:
  user_provider.dart L118-L130: two separate await update() calls without batching.

Risk: Orphaned route assignments. Sellers unable to create sales until admin re-edits.
  isSellerForRoute() Firestore rule denies all seller-write operations.

Fix:
  Convert both writes into a single WriteBatch.

  STATUS: ✅ FIXED IN THIS PATCH (see implementation section)
Effort: S
