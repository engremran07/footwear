4) Main Findings
----------------

4.1 Sessions and Device Pairing Purge
- The codebase work on app-managed session/device pairing was intentionally removed, and the current runtime contract keeps Firebase Authentication as the only sign-in mechanism.
- The final intent was zero-trace, zero-tolerance for session/device-pairing artifacts and custom access-slot logic. This is aligned with the project’s later work to strip deprecated pairing and session features from the app path and rules.
- The app continues to use role and tenant context checks, with workspace-admin and tenant-admin logic treated as business-scoped, not as custom session enforcement.

4.2 CRUD and Sorting Restoration
- Business CRUD and route/shop/transaction/invoice access were re-audited and restored to tenant-scoped patterns for workspace admins.
- The project intentionally moved away from session/device policy, and kept the safe modernized architecture: Auth + role + tenant + workspace context, not app-managed device pairing or extra access-slot logic.
- The user’s request to remove soft-delete behavior was addressed by keeping hard-delete and ordinary CRUD logic anchored to the provider and rules path, while avoiding unnecessary soft-delete reintroductions in the current work.

4.3 Financial Integrity / Invoice / Transaction Audit
- The user’s financial reports were correctly treated as a critical business path: workspace admins were checked for transaction/invoice permission gaps.
- The root issue was not “sellers vs admins only”; it was a combination of role/tenant alignment, provider guards, Firestore rules layers, atomic balance updates, and targeted regression tests.
- Correct behavior retained:
  - `shop.balance` remains the sole financial source of truth,
  - writes must be atomic via provider notifier batch/transaction logic,
  - standalone ledger rows require same-batch shop balance updates,
  - invoice-linked flows and invoice voids remain guarded,
  - bad-debt and write-off logic is validated through atomic workflows,
  - soft deletes for standalone cash rows are not the default allowed path in the user’s desired final behavior.

4.4 Arabic/Urdu Export Rendering Audit
- The export issue was traced to the shared export system, not a single screen.
- Findings:
  - PNG exports are rasterized from generated PDF bytes; therefore any PDF text/layout problem automatically affects image exports.
  - The `pdf` package’s Arabic shaping logic is only active when `--dart-define=use_arabic=true` is set.
  - Mixed-string RTL detection is currently coarse: if a cell contains any Arabic/Urdu character, it may be treated as RTL as a whole, which can reorder mixed strings containing numbers, IDs, Latin text, dates, and currency values.
  - The app uses a Noto Sans Arabic PDF font as the main font, with Nastaliq as fallback only, because complex Urdu shaping is not reliable as a primary PDF font for the current package.
  - Excel export preserves Unicode but is limited by the spreadsheet client’s font/rendering behavior; this is a separate concern from the PDF path.
