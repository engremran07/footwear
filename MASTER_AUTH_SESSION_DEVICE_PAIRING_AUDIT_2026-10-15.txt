EXECUTIVE SUMMARY

There is no unconditional code path that signs out every user immediately after correct credentials. There are, however, two credible and reproducible post-authentication defects that can cause immediate logout on affected device/session histories:

1. Registration allocates device and session slots independently, then validates clock skew against deviceRefs[session.slotNumber]. Session slot number is not device slot number. When they differ, the new login can be checked against another device's old last_seen_at; a timestamp over five minutes old is misclassified as device clock skew, the just-created session is revoked, and AuthNotifier signs out.
2. SessionGuard starts an access query when the auth profile first appears, before sign-in registration has necessarily completed. If that query returns a pre-registration revoked-session snapshot after registration succeeds, the guard can sign out. A 15-second registration-grace policy exists but is not wired into enforcement. The post-registration auth notifier event can be dropped while the stale check is still in progress.

A third direct path is intentional policy behavior: if pairing is required, a new device is stored as pending, the sign-in flow turns pending into an error, and Firebase Auth is signed out. A blocked device, reset-required device, exhausted slot limit, invalid/inactive profile, missing tenant assignment, or registration permission/network error also rolls back the Firebase sign-in. These cases must be distinguished from a silent runtime logout by capturing the mapped login error and auth event sequence.

Overall severity: HIGH. The slot-index mismatch and stale session-check race can reject a legitimate login without a user-caused credential error. Session revocation and device-administration workflows are also inconsistent, and tenant-admin security controls currently route to a screen that the router blocks.

1. INCIDENT PATH AND DIAGNOSIS

Normal tenant sign-in sequence:

1. LoginScreen calls AuthNotifier.signIn(email, password).
2. Firebase Auth accepts credentials and emits the authenticated UID.
3. AuthNotifier fetches users/{uid}; it rejects missing, inactive, unsupported-role, and workspace-unassigned profiles.
4. Tenant users call SessionManagementNotifier.registerCurrentAccess; super-admin users call registerPlatformSession.
5. Registration writes or refreshes device/session records. For tenant users it then performs a server read and a clock-skew check.
6. AuthNotifier completes. The router redirects from /login to / after auth/profile state settles.
7. SessionGuard independently queries server sessions/devices, enforces revoked/blocked/expiry states, and arms renewal/expiry timers.

Direct source evidence:
- app/lib/providers/auth_provider.dart: signIn enters AsyncLoading before Firebase Auth; all registration exceptions are caught, cleanup is attempted, then FirebaseAuth.instance.signOut() is called.
- app/lib/providers/tenant_provider.dart: registerCurrentAccess independently selects deviceIndex and sessionIndex, writes device_slot_id, then validates the device timestamp using deviceRefs[session.slotNumber].
- app/lib/core/services/session_guard.dart: profile and auth-notifier listeners can both request access verification; a running access check causes the second request to return.
- app/lib/core/router/app_router.dart: router holds /login while auth notifier is loading, then routes based on auth/profile state. Router navigation itself does not call Firebase Auth signOut.

Diagnostic decision tree for the affected device:
- If the login UI reports device-pairing-pending, device-admin-reset-required, device-blocked, device-limit-reached, session-limit-reached, or device-clock-skew, the post-credential registration policy/path is directly implicated.
- If FirebaseAuth.currentUser becomes null, identify the exact signOut caller: AuthNotifier.signIn rollback, SessionGuard enforcement, startup deferred token refresh, explicit user action, or auth persistence.
- If the UI redirects to /login while FirebaseAuth.currentUser remains non-null, investigate authStateProvider stream error/null/persistence and RouterNotifier. Do not call this a Firebase sign-out until the UID is checked.
- Capture the same timestamped sequence for UID, normalized role, tenant_id or active_workspace_id, device installation ID, selected device slot, selected session slot, device status, session status/expires_at, last_seen_at, pairing policy, and mapped error.

2. PRIORITY FINDINGS

FINDING AUTH-001 | P1 | TENANT ACCESS REGISTRATION | HIGH CONFIDENCE

Title: Clock-skew validation indexes a device slot with the independent session slot number.

File: app/lib/providers/tenant_provider.dart (registerCurrentAccess, post-commit verification near lines 770-780)
Evidence:
- Device selection computes deviceIndex from device registration records.
- Session selection independently computes sessionIndex from session records.
- Session data stores both slot_number: sessionIndex and device_slot_id: deviceRef.id.
- After commit, the verifier reads deviceRefs[session.slotNumber] instead of the device reference encoded by session.deviceSlotId/deviceIndex.
- If that different device's last_seen_at differs from the local clock by over five minutes, registration terminates the current session and throws device-clock-skew.
- AuthNotifier.signIn catches registration errors and signs out.

Impact: A valid login can create its session, then immediately revoke it and sign out when device/session slot allocation histories differ. The two slot spaces are intentionally independent, so equality cannot be assumed. This is the strongest concrete match for the reported immediate logout, conditional on a slot mismatch and a sufficiently old timestamp.

Reproduction:
1. Have a user with at least two device records and session records whose reusable slot indexes differ (for example, device 0 remains active after logout while session 0 is revoked/reused).
2. Register or log in from a second device; force deviceIndex != sessionIndex.
3. Make the device record currently at deviceRefs[sessionIndex] have last_seen_at older than five minutes.
4. Observe the newly created session being revoked, device-clock-skew returned, and Firebase Auth signed out.

Recommendation: Resolve the device reference from the selected device index/slot ID, not session.slotNumber. Validate that the fetched document's device_id equals the current installation ID before applying clock-skew policy. Add a regression where deviceIndex != sessionIndex and the other device has an old timestamp.

FINDING AUTH-002 | P1 | SESSION GUARD / LOGIN RACE | HIGH CONFIDENCE IN RACE, CONDITIONAL INCIDENT CAUSE

Title: A pre-registration session snapshot may be enforced after successful registration.

Files: app/lib/core/services/session_guard.dart; app/lib/core/utils/session_access_policy.dart; app/test/unit/models/session_access_policy_test.dart
Evidence:
- The authUserProvider listener starts _verifyCurrentAccessSession when a profile first appears.
- That method starts a server query before checking whether AuthNotifier.signIn is still loading; the downstream enforcement does return while loading.
- The query may have captured a pre-registration revoked session. If it completes after signIn changes AuthNotifier state to AsyncData, the revoked result can now pass the loading check and sign out.
- The authNotifierProvider listener requests a fresh check after login loading ends, but _accessCheckInProgress causes that request to return if the stale check is still active.
- SessionAccessPolicy.shouldDeferMissingSessionEnforcement and its 15-second registration grace exist, but SessionGuard does not call the helper.

Impact: A logout/previous revoked slot can race a successful re-login on the same installation. This is timing-dependent, not a deterministic every-login failure.

Reproduction/test: Gate the server session query started by profile hydration; complete registration and AuthNotifier.signIn; then release the pre-registration revoked result. Assert that the guard does not sign out and performs an authoritative post-registration verification.

Recommendation: Defer enforcement while sign-in/registration is loading and use the existing registration grace only for the current UID. Do not drop the authoritative post-registration check when a stale check is in progress; queue and rerun it after the current query completes.

FINDING AUTH-003 | P1 | DEVICE ADMINISTRATION / FIRESTORE READS | HIGH CONFIDENCE

Title: Admin revoke/block reads all fixed session slots, including missing documents that admin rules cannot read.

Files: app/lib/providers/tenant_provider.dart (_setDeviceAccess); firestore.rules (users/{userId}/sessions/{slotId} get rule)
Evidence:
- _setDeviceAccess builds ten fixed sessionRefs and performs transaction.get on every slot, even when many have never been created.
- The session get rule authorizes a workspace admin using resource.data.tenant_id. A nonexistent slot has no tenant_id/resource data to establish that authorization.
- The transaction can therefore fail before it updates the device or revokes any active session.

Impact: Workspace-admin and selected-super-admin remove/block actions may fail for ordinary users with unused session slots. This undermines the administrative control plane and can leave access active.

Recommendation: Make missing-slot reads deliberately authorizable only for a canonical slot path under a user document whose tenant is in the caller's scope, or redesign the transaction to read only existing authorized records with a race-safe strategy. Add an emulator test invoking the actual notifier read shape against a user with one session and multiple absent slots.

FINDING AUTH-004 | P1 | SESSION REVOCATION SEMANTICS | HIGH CONFIDENCE

Title: Tenant session revocation is eligible for automatic reactivation during renewal.

Files: app/lib/providers/tenant_provider.dart (registerCurrentAccess and terminateSession); app/lib/core/services/session_guard.dart (_renewCurrentAccessSession); firestore.rules (session update revoked-to-active branch)
Evidence:
- terminateSession marks a session revoked.
- registerCurrentAccess does not reject a revoked session slot when selecting a reusable session slot; it writes a new active session there if the device remains active and policy allows reuse.
- SessionGuard automatically calls registerCurrentAccess every ten minutes.
- Rules permit owner reactivation of a revoked session if the device registration is active.

Impact: An administrator's terminate-session action can be undone by client renewal, depending on ordering. If the guard checks first, it signs out; if renewal wins, the session can become active again. This is not a reliable revocation boundary and must not be represented as server-enforced access control.

Recommendation: Define explicit semantics: device/session termination must be durable until a fresh interactive sign-in or administrator reset. Make renewal reject revoked state; preserve the repository's limitation that ordinary Firestore requests are not bound to these session IDs under Spark.

FINDING AUTH-005 | P1/P2 | TENANT ADMIN ROUTING | HIGH CONFIDENCE

Title: Tenant-admin device security link is visible but the router rejects its route.

Files: app/lib/screens/tenant_management_screen.dart; app/lib/core/router/app_router.dart; app/lib/core/utils/role_utils.dart
Evidence:
- Tenant management screen shows a security icon for tenant admins.
- The icon pushes /tenants/{tenantId}/security.
- _isTenantManagementPath includes that path.
- Router permits tenant management paths only when canManageWorkspaceRole(role) is true; that predicate returns true only for super_admin.

Impact: Tenant admins tap a visible device/security action and are redirected to /. They can reach /profile/security for their own usage, but not the workspace-wide approve/remove/block/reset controls promised by the tenant management UI.

Recommendation: Define route authorization separately for platform workspace selection and same-tenant security administration. Check tenant_admin ownership/current tenant on the target tenant ID; keep super-admin access bound to active_workspace_id. Add router tests for admin, tenant_admin, unselected super_admin, and selected super_admin targeting own vs other tenant.

FINDING AUTH-006 | P2 | SIGN-IN ROLLBACK | HIGH CONFIDENCE

Title: Any registration exception signs out, including transient Firestore/network errors.

File: app/lib/providers/auth_provider.dart (tenant and platform registration catch blocks)
Evidence:
- Firebase Auth credential sign-in succeeds before profile/access registration.
- Both registration catch blocks attempt cleanup, then call FirebaseAuth.instance.signOut() unconditionally and rethrow.
- This includes permission-denied, unavailable, deadline, failed-precondition/index, and unexpected local exceptions, not only permanent policy rejection.

Impact: A transient access-registration failure appears as “login succeeded then logged out.” The UI receives an error, but user-visible status may be too generic to distinguish pairing, policy, network, and rules failures.

Recommendation: Preserve fail-closed behavior where required, but classify registration errors, keep the real mapped cause visible, check Firebase current UID before rollback, and avoid signing out a different account. Add tests for permanent policy denial, pending approval, transient network failure, and account-switch races.

FINDING AUTH-007 | P2 | FIREBASE UID RACE | HIGH CONFIDENCE IN MISSING GUARD

Title: Several sign-in rollback and startup token-refresh paths sign out the global current user without a UID recheck.

Files: app/lib/providers/auth_provider.dart; app/lib/main.dart
Evidence:
- Login captures uid, but missing-profile/role/tenant/inactive and registration rollback paths call FirebaseAuth.instance.signOut() without verifying that currentUser.uid is still the captured uid.
- main.dart deferred token refresh captures a User, then on a terminal refresh exception signs out FirebaseAuth.instance without confirming the current UID still matches.
- Resume verification has a UID recheck, demonstrating the intended safer pattern elsewhere.

Impact: If another auth event/account switch occurs while a delayed request is in flight, a stale failure for account A can sign out a newly current account B.

Recommendation: Centralize a signOutIfCurrentUid(expectedUid) helper and use it in all async rollback/refresh paths. Test delayed failure for A after switching to B.

FINDING AUTH-008 | P2 | SESSION LIFECYCLE | HIGH CONFIDENCE

Title: Renewal timer is canceled on app pause and not restarted on resume.

File: app/lib/core/services/session_guard.dart
Evidence:
- _onAppPaused cancels _renewalTimer.
- _onAppResumed verifies access and restarts inactivity handling, but does not call _startSessionRenewal.
- Renewal starts only when authUserProvider changes UID, so an app that pauses/resumes can remain foregrounded without periodic session renewal.

Impact: A resumed app may later hit the old expiry timer and sign out despite continued use.

Recommendation: Restart renewal after successful resume/auth verification for the same UID. Test pause/resume, verify renewal timer is rearmed, and advance past the original expiry while before the renewed expiry.

FINDING AUTH-009 | P2 | DEVICE CLOCK / SERVER TIME | HIGH CONFIDENCE

Title: Session expiry is generated from local device time before server-side TTL validation.

Files: app/lib/providers/tenant_provider.dart; firestore.rules
Evidence:
- Tenant and platform session expires_at use DateTime.now() + 7h50m.
- Rules validate expires_at against request.time and cap it at 12h.
- A local clock sufficiently ahead/behind can cause registration permission denial; login catches that failure and signs out.
- The server timestamp comparison after tenant registration occurs only after the transaction commits and therefore cannot protect the expiry write from clock-based rule rejection.

Impact: Devices with significantly incorrect clocks can authenticate credentials, then fail access registration and be logged out. Stale-device detection also uses client time while Rules enforce a server-time 30-day threshold.

Recommendation: Derive expiry/age decisions from server time or use a bounded server-time offset; expose clock-skew guidance before registration writes. Add tenant and platform rules-emulator tests around skewed time boundaries.

FINDING AUTH-010 | P2 | PROFILE STREAM / STALE CACHE | CONDITIONAL

Title: An inactive initial profile emission can trigger remote-inactive sign-out without waiting for server confirmation.

Files: app/lib/providers/auth_provider.dart; app/lib/core/services/session_guard.dart
Evidence:
- authUserProvider maps Firestore profile snapshots directly into UserModel.
- SessionGuard signs out whenever the profile stream emits active == false; it does not distinguish cached initial data from a server-confirmed snapshot or wait for sign-in registration to settle.
- The registration grace helper is not used here.

Impact: If local persistence contains an old inactive profile while the server profile is active, the first cached emission may sign out a valid session. This is conditional and requires stale local/server divergence.

Recommendation: Make the guard wait for confirmed profile/access state, not just a cached boolean. Test inactive cached snapshot followed by active server snapshot.

FINDING AUTH-011 | P2 | INSTALLATION ID / REINSTALL | CONFIRMED POLICY PATH

Title: Clearing application storage creates a new installation identity and can require approval or exceed slot limits.

File: app/lib/core/services/device_installation.dart
Evidence:
- Installation ID is a UUID stored in SharedPreferences and created when absent.
- An ordinary same-package Android APK update should preserve app data; uninstall, clear-data, web origin change, or browser storage clear can generate a new ID.
- Pairing-enabled new IDs become pending; slot exhaustion/blocked/reset policy errors cause sign-in rollback.

Impact: Reinstall/data reset may look like “new APK login logs out.” This is expected policy, not proof that an in-place update rotated the ID.

Recommendation: Label this as installation identity, explain the admin approval/reset step, show the specific pending/limit error, and monitor save failures. Do not silently weaken pairing to work around it.

FINDING AUTH-012 | P2 | APP CHECK FAILURE UI | CONFIGURATION-DEPENDENT

Title: App Check activation errors can be logged while the normal app shell continues.

File: app/lib/main.dart

Evidence:

FINDING AUTH-020 | P2 | SUPER-ADMIN SESSION CONTROL | HIGH CONFIDENCE

Title: Platform-session termination can be undone by automatic renewal.

Files: app/lib/providers/tenant_provider.dart; app/lib/core/services/session_guard.dart
Evidence:
- registerPlatformSession queries only active sessions for a device and creates a new active session when none is found.

Recommendation: Make revoked platform session an explicit registration denial until fresh sign-in or admin reset; test renewal racing with platform termination.

3. EXPECTED SIGN-OUT CONDITIONS (NOT THEMSELVES BUGS)

The following code paths intentionally revoke Firebase Auth after credentials are accepted. They must show the specific actionable error; users should not interpret them as password failure:
- Firestore profile is missing, role is unsupported, account is inactive, or a non-super-admin has no tenant assignment.
- Workspace pairing is required and the installation is pending approval. Approval does not auto-complete the already-failed sign-in; user must retry. Device-limit/session-limit exhaustion, blocked device, and admin-reset-only revoked device also reject registration.
- Tenant/platform session registration fails for any reason; current code signs out after cleanup, including transient network/permission failures (AUTH-006).
- Registration's post-commit timestamp check reports device-clock-skew (AUTH-001/AUTH-009).
- SessionGuard finds current installation blocked, has a revoked session, has missing expiry, or reaches the access expiry timer.
- Admin inactivity/background limits are reached (see current defaults in session_guard.dart; super_admin is classified as admin for those limits).
- `rememberMe` is false on app startup, so main.dart signs out the restored Firebase session by design.

4. ADMIN AND SUPER-ADMIN DEVICE-PAIRING CONTROL PLANE

Existing controls:
- Workspace policy contains require_device_pairing, allow_admin_reset_only, max_devices_allowed, and max_active_sessions_allowed.
- Defaults are three device slots and two active session slots; pairing and admin-reset-only behavior are configurable.
- Device screen includes own-device usage, tenant registry devices/sessions, pending approval, remove/revoke, block, reset, terminate session, and platform-session management.
- Super-admin tenant business access is scoped by active_workspace_id and support reason in Firestore Rules; client screens do not replace those Rules.

Missing/misaligned wiring:
- Tenant admins see a tenant security link but router rejects it (AUTH-005).
- Admin revoke/block transaction reads ten session docs including absent slots, which current admin get rules likely deny (AUTH-003); exercise actual notifier operation in emulator before relying on it.
- Session search does not filter the Sessions tab; pagination/truncation and retry are incomplete (AUTH-013/AUTH-014).
- Block is terminal and has no recovery path (AUTH-015).
- Selected super-admin foreign security URL remains on the URL but shows unavailable rather than redirecting (AUTH-017).
- Selected super-admin dashboard remains platform-wide metadata rather than selected-workspace metrics (AUTH-018).
- Workspace switching/sign-out does not guarantee a complete start/end support-access log under failure (AUTH-019).
- Session termination/revocation can be undone by renewal (AUTH-004/AUTH-020).
- Tenant policy owner authority conflicts across docs, UI, provider, and Rules (AUTH-016/AUTH-023).

5. TEST AND OBSERVABILITY GAPS

Observed existing tests cover pure auth refresh policy, device display-name formatting, role parsing, access-policy selection/clock-skew/grace helper, dashboard startup, and Firestore rule slot/query/approval/revocation cases. They do not cover the critical app lifecycle edges:
- AuthNotifier sign-in success through profile and access-registration completion.
- Device slot index different from session slot index.
- Delayed pre-registration session read enforced after sign-in completes.
- Registration rollback after transient network/permission error and UID change during await.
- Same-UID role changes and timer reset.
- Pausing/resuming and renewal timer re-arming.
- Admin revoke/block notifier with missing session slot docs.
- Revocation vs renewal race for tenant and platform sessions.
