1. EXECUTIVE RESULT

The code-level purge is implemented in the current worktree. The app no longer
registers devices, requires pairing approval, allocates custom access slots,
renews custom sessions, or wraps authenticated navigation in a custom session
guard. The related screens, routes, models, services, localization strings,
collection constants, Firestore Rules paths/helpers, and dedicated indexes
were removed.

Firebase Authentication remains. Active user-profile checks, role checks,
tenant isolation, super-admin selected-workspace context, the eight-hour
support-context Rules limit, and append-only platform_access_logs remain.
These are separate identity, authorization, and audit controls, not device
pairing or custom sign-in slots.

Workspace-admin route, shop, and transaction CRUD paths are tenant-scoped and
covered by Rules regression tests. Shop creation plus route-count reconciliation
and ledger creation plus shop-balance changes are exercised as atomic batches.
Existing sort providers, comparators, filters, and query ordering were not
rewritten.

Rules/indexes and Hosting were deployed to `shoeserp-clean-20260327`; the web
release and ABI-split APKs were built, and the ARM64 APK was copied to and
installed on phone `R5GL22RGT9V`. Deployment did not delete legacy Firestore
records or Firebase Auth accounts. Commit/push will be recorded in section 7
after the final diff review.


2. IMPORTANT SCOPE AND DELETION POLICY

Authentication:
- Firebase Auth remains the only sign-in mechanism. Firebase SDK token
  lifecycle and web persistence remain in place.
- Sign-in validates an active Firestore profile, canonical role, and tenant
  assignment. It does not call custom device/session registration.
- Super-admin business access still requires an explicitly selected workspace,
  a reason, append-only start/end records, and an eight-hour Rules-enforced
  context. This is retained by design.

Existing Firestore data:
- No production data was read, migrated, or deleted in this implementation.
- Existing users/{uid}/sessions, device_registrations, platform_sessions, or
  legacy device-policy fields, if present, are inert from this source tree;
  removing app references and Rules paths does not erase stored documents.
- Data cleanup must be a separately reviewed, backed-up, dry-run migration
  against an explicitly confirmed Firebase project. platform_access_logs and
  Firebase Auth identities are not part of such cleanup.

Delete behavior:
- No new soft-delete behavior was added as part of this purge.
- Existing standalone cash-in/cash-out correction remains an audited soft
  delete with an exact same-batch shop.balance reversal. This is required by
  the repository's financial-integrity contract; hard deletion or removing the
  reversal would corrupt balances and financial history.
- Invoice-linked transactions remain protected and are corrected only through
  invoice void/credit-note flows. Referenced routes/shops retain their existing
  safe deactivation behavior; physical deletion remains governed by existing
  reference and role safeguards.

5A. FIRESTORE RULES REMEDIATION ADDENDUM — 2026-10-22

An additional local Rules audit identified these gaps:
- Shop creation could supply a nonzero opening balance and cached last-
  transaction values.
- Admin or seller transaction creation could produce an orphan/mismatched
  ledger row without its corresponding same-batch shop/balance write.
- An active member profile could retain business access when its tenant
  document was inactive.

Local remediation:
- `isAdminForTenant` now checks privileged role/tenant eligibility before
  loading tenant status. Ordinary tenant-admin and seller business access
  requires the tenant document to be active. Selected super-admin restoration
  remains a separate, explicit path.
- Shop creates require `balance == 0` and reject seeded cached last-
  transaction metadata.
- Standalone transactions require an exact linked shop/balance change in the
  same atomic write. Invoice-linked seller entries use invoice references and
  the existing invoice/shop aggregate checks rather than duplicating expensive
  per-row balance calculations. This preserves multi-row invoices and avoids
  Firestore's expression-evaluation ceiling.
- Regression tests cover inactive-tenant access with active profiles, a
  nonzero shop opening balance, orphan/mismatched ledger writes, and valid
  tenant restore behavior.
